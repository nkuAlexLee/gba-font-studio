## 2026-09-06 回填闭环：终止符碰撞的三层结构（EliteRedux 全量回填）

- **碰撞实际分三层**，restore-tails 一趟只解决前两层：
  1. byte-fix 可修的 ASCII 结尾碰撞（28 处）
  2. CJK 结尾碰撞（9 处）——byte-fix 会切碎 F7+hi+lo，必须 CSV 缩短译文重插
  3. **双重级联碰撞**（4 处，新发现）——byte-fix 把终止符从 a+1 挪到 a，而 a 本身也是指针
     目标（指向 "a"/"I" 类单字母微串）；且脚本守卫看到 [F7 hi lo][ASCII→FF] 的
     cur[a-3]==F7 特征会误判"CJK 截断"拒绝再修 → 永久残留。判据：最终产物上
     run-start a 无 owner 行（start+len ∉ {a,a+1}）且 base[a] 是字母 → 往上游找
     start+len==a+1/a+2 的行。
- **修复模式**：CSV 行译文缩短 ≥3B（删 1 汉字或布局 token+1 汉字），终止符退到
  min(指针目标)-1 之前，重插后字节自然还原。
- **定位工具**：终扫脚本必须扫**最终产物**（tails 后）而非 insert 输出；owner 归因
  必须用 normalizeText 后的编码长度（标点归一化会变长）。
- **别名行教训**：跳空格别名（en 3 前导空格 + 指针指 +3）的行，译文必须带同样前导
  空格——上轮产物丢空格 → 别名指针读到位。本次顺手补全了译文（水/电/虫/冰 类型提示行）。
- **战果**：out/汉化输出-tails.gba 终扫碰撞 0；27359 条写入（20386 原地 + 6973 repoint，
  append 区 0x35ECC）；GSW 补丁已上。

## 2026-09-06 双字节方案实验：原理可行、引擎不可行（ EliteRedux 实证闭环）

- **问题**：ESC 3B/汉字导致超长桶与预算压力，能否改双字节 2B/汉字？
- **容量审计 ✓**：扫描 34691 行登记原文（200 万字节）得 **66 个完全未用单字节**
  （0x60-0x78/0x7D-0x7F 连续段），28 引导码 × 247 有效记录 = 6916 ≥ 6768 汉字。
  渲染钩子改造也是小改（LUT 查表替代 F7 判定，指令更少）。
- **★引擎阻断（决定性发现）**：双字节流在**脚本引擎的文本拷贝器**（ROM→EWRAM）被损坏
  ——EWRAM 缓冲区整段变成 0x11 填充，渲染器读到的是垃圾而非原文。原引擎只透传它认识的
  控制码流；自造引导码无引擎侧支持。**ESC 路线的真正优势 = F7 骑在引擎现成的 F7
  控制码处理上**（动态缓冲区打印，已中和为跳过），3 字节序列无损流过拷贝器。
- **双字节要成立需要**：找到并补丁拷贝器 + 换行计算 + 所有文本遍历例程（每处都要
  lead+lo 原子消费）＝深度引擎逆向，风险远超收益。**结论：ESC 是 ER 的正解，封板。**
- **方法论（本次最有价值的工具套路）**：
  1. romctl `/hookadd?addr=0x08257098&xregs=0,1` 抓渲染器字符流 + 冻结态 `/memread`
     采样 EWRAM 缓冲区 → 10 分钟定位"拷贝器损坏"，胜过数小时静态猜测；
  2. 码表贪心解码歧义：`04 00`（图标+空格）会被 4 位码 `0400=肤` 吞并 → **解码器输出
     的怪字要先怀疑歧义再怀疑 ROM**（渲染端画字形无此问题）；
  3. 字节补丁脚本的幂等现场检查会把"另一编码的合法写入"误判为不匹配 → 重跑前先
     明确现场该是什么编码。

## 2026-09-07 小字体推进机制深挖：ER 画布渲染链全解码（实验②③⑤）

- **仪器突破**：romctl hookadd 必须挂**偶数地址**（Thumb PC 对齐，奇数钩子永不触发）；
  汉字 blit 快照仪（RT_HOOK 第 4 次 blitter 返回地址改指拷贝循环 → EWRAM 0x0203E000）

  代码必须成为返回目标，否则是死代码。
- **渲染链全貌**（Elite Redux 自定义 UI）：RenderText(hook) → blitter(0x082562A9,
  调色板 LUT 式 2bpp→码流展开器, LUT@0x090191E0, 状态表@0x03005550, 16B src→32B dst)
  → WORKBUF(0x03005600, 每字形 128B=4×32B tile) → RT_SUCC(0x0825728C) 无条件消费
  [buf+0x80]=宽度推进光标 → 合成器(0x082563BC) 按 **4B/行** 读 WORKBUF 写入
  **位图上下文**（表@0x0203F748, 每项 12B: [3]×8=画布宽240 [4]×8=高160 word@8=画布指针）。
  画布=2bpp/4bpp 位图（非 VRAM tile!），ER 全 UI 走此路径；对话文本仍走原版 tile 路径。
- **实证链**：blit 事件（src=0x98xxxx 确认 fontid-0 分支触发 ✓）；快照 v3 确认 blit
  产物=合法码流（行 0-7 墨码/行 8-31 透明码 ✓ bg=0 修复生效 ✓）；**但屏幕仍乱码** ⇒
  码流→画布的映射环节存在未解码的坐标/状态机变换（合成器 137 次/帧 = 每字形多 pass，
  描述符 r0 含画布指针/裁剪参数，双 pass 基址 0x5600/0x5620 的语义未定）。
- **已排除**：小字库数据错误（ROM 逐字节比对 ✓）；0x1800000 踩踏（原版该区全 FF ✓）；
  宽度参数不被消费（RT_SUCC 无条件 add ✓）；bg=3 阴影方块（0 填充后依旧乱码 ✓）。
