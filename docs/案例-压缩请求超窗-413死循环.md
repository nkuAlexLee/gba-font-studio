# 案例：压缩请求自身超窗 → `side_request_payload_too_large` 413 死循环

> 记录时间：2026-10-04（现场数据 2026-10-03 ~ 10-04）
> 环境：Pi Web 安装版（`D:\Program Files\Pi Web`）+ billion-context 代理 0.1.179 + pi-coding-agent 0.85.1
> 模型：`DeepSeek-V4.1-Flash`（provider `ark-agent-plan`，窗口 1,048,576 / 输出上限 104,800）
> 定位状态：链路、调用方、根因**已闭环**；「压缩请求 why 被判成 side request」的**最后一环未闭环**（见 §6）

---

## 1. 症状

auto-compact 扩展每 5 分钟报一次，工作台里表现为「自动压缩失败」：

```
Summarization failed: 413: {"type":"server_error","code":"side_request_payload_too_large",
"message":"side request payload ~1849705 tokens reaches the effective context window 1048575
(model=DeepSeek-V4.1-Flash); NOT forwarded — side requests (max_tokens<=200) bypass compression
by design (#388). Shrink the conversation or raise the model's context window.","retryable":false}
```

代理侧同一时刻的 warn（`logs` 见 §4）：

```
side request (~1849705 tokens) ≥ effective window 1048575 (model=DeepSeek-V4.1-Flash)
— NOT forwarded: guaranteed upstream 400 (side requests bypass preflight by design, #388)
```

注意文案自相矛盾的两处：`effective window 1048575`（= 模型窗口 1,048,576 − 1）与退出码里的
`side requests (max_tokens<=200)`——**请求被判成「侧请求」，于是被设计性地跳过压缩**。

---

## 2. 触发链路（5 步）

1. 出事会话（workspace 会话，id `01a0fb6e-0956-7033-8b6d-60d84a4d9945`，cwd
   `D:\Program Files\Pi Web\data\workspace`）Jsonl 已 **648,891,269 B / 13,270 行**，最大单行
   **7,840,145 字符**（base64 图片 + 巨量 tool 输出）；代理侧账本 `rawInputTokens 11,825,492`。
2. 该轮 preflight（代理的本地压缩）卡死：唯一可压范围被「会切断工具调用回合」拒两次 → 放软
   保护带重试 → 30s 宽限后仍无进展（`preflight still running after 30000ms grace`）→ 客户端断开，
   最终只压掉 1 个范围（`~2026 tokens saved (8999006 → 236608) in 36955ms`），并留下
   `[acp-drift] fold coverage mismatch: 5802/7550 covered message id(s) … 1748 missing`
   → `preflight aborted (the client disconnected during preflight compression); not forwarding`。
3. pi 侧启动自己的压缩（auto-compact → `ctx.compact()`）：`serializeConversation()` 把**整段历史**
   序列化成纯文本塞进单个 `<conversation>…</conversation>`，因此请求**恰好 2 条消息、无 tools**
   （代理日志：`request: 2 msgs, inbound=7.2MiB`）。pi 的摘要输出预算是
   `maxTokens = min(floor(0.8 × reserveTokens), model.maxTokens)`（`xp3/dist/core/compaction/compaction.js:489`），
   与本机 `compaction.reserveTokens=131072` 一起给出 `min(104857, 104800) = 104800`——**与输入体量无关**。
4. 代理 `isSideRequest()` 把它判为**侧请求**：判定只有两条路——`x-bili-plugin-agent: title`，或
   「无 tools 且输出预算字段（`max_tokens`/`max_completion_tokens`/`max_output_tokens`）取值 ≤
   `SIDE_REQUEST_MAX_TOKENS=200`」。侧请求按 #388 设计**原样转发、不走压缩**（`sidePassthrough`）。
5. `sideRequestGuard` 计算 `estimate ≈ 1,849,705 tokens` ≥ `1048575 × 1.15(TOLERANCE)` → 本地
   `writeHead(413)` 直接打回，不转发。pi 的 `retryAssistantCall` 重试 4 次全灭 → 报
   `Summarization failed: 413: …` → auto-compact 退避 5 分钟 → 历史继续变大 → 下一轮同样失败。

**死循环**：历史太大 → 要压缩 → 压缩请求本身就要塞整段历史（1.85M tokens）→ 被拦 → 历史继续变大。

## 3. 关键代码位置（复核过的判定链）

代理 `D:\Program Files\Pi Web\data\agent\npm\node_modules\billion-context\dist\index.js`：

- `SIDE_REQUEST_MAX_TOKENS = 200`、`SIDE_REQUEST_AGENTS = new Set(["title"])`
- `isSideRequest(parsed, requestAgent)`：
  `agent 命中集合 → true`；`Array.isArray(parsed.tools) && parsed.tools.length > 0 → false`；
  否则取 `outputBudgetField(parsed)`（顺序 `max_tokens` → `max_completion_tokens` →
  `max_output_tokens`，再退 `generationConfig.maxOutputTokens`），`0 < raw ≤ 200 → true`。
- `pluginRequestAgentHeader(headers)`：**必须先有 `x-bili-plugin` 头**才读 `x-bili-plugin-agent`。
- `sideRequestGuard(parsed, protocol, modelContextLimit, imageBilling, headroomCap, armedLimit)`：
  `estimate = estimateRawBodyTokens(parsed) + imageTokensInParsedBody(...)`；

- 命中即 `res.writeHead(413, …)`（消息即 §1 文案），**不转发也不压缩**。

  **该 info 形态在 3 天日志里 0 条** ⇒ 只有本次 16 条被判为侧请求，且全部被拦。
- `restoreOutputBudget(...)` 紧放在守卫之前：读到 `value > 200` 时**只记 highWater**不降值；
  `value ≤ 200` 且 **tools 为空则直接 return**（保持侧请求判定）；只有 tools 非空才抬回 ceiling。
- 另有 `clampOutputBudget`：只作用于**压缩后的 rebuilt body**（日志里 `output budget clamped` 值为
  384000→176376、512000→{99285…509233} 等，量级远超 200），不是入站预算。
- dump 只能靠**进程 env**（无法运行时开启）：`ACP_DUMP_BODY="1"`，
  目录 `ACP_DUMP_DIR` 或默认 `stateDir()/dumps`（`C:\Users\nkualexlee\.local\state\billion-context\dumps`，现不存在）。

pi 侧 `D:\Program Files\Pi Web\payload\pi-web\.next\node_modules\xp3\dist\core\compaction\compaction.js`：

- `:489` `const maxTokens = Math.min(Math.floor(0.8 * reserveTokens), model.maxTokens > 0 ? model.maxTokens : POSITIVE_INFINITY);`
- `:475` `buildSummarizationContext(promptText)` → `{systemPrompt: SUMMARIZATION_SYSTEM_PROMPT, messages:[1 条 user]}`
  ⇒ 压缩请求恒为 **2 条消息、无 tools、纯文本**。

- `:429-437` `getSummarizationFailure`：`stopReason === "length"` → `generation hit the token cap and the summary is incomplete`（**部分摘要一律不落盘**）；`stopReason === "error"` → 直接贴上游/代理错误文本（本 413 走这条）。
- 客户端从不打 `x-bili-plugin-agent`：pi 插件 `dist/agent/pi-native.js` 只写
  `x-bili-plugin` / `-conversation` / `-context-window` / `-max-output`（= `Math.floor(ctx.model.maxTokens)`）/ `-model`；

## 5. 为什么「修剪会话」只是推迟，而不是根治

压缩请求体量与历史体量同阶（都要塞整段历史）。只要单会话历史再次超过模型窗口，
压缩请求就必然再次超窗、再次被 413（16 条 warn 里 estimate 从 1.85M 涨到 2.19M 就是随历史增长）。
另见 §4 的两条成功样本（21 万 / 25.5 万 tokens 时压缩正常 `done compactions=1`）——
**失败纯粹由体量驱动**，不是配置损坏。

## 6. 未闭环的一环：压缩请求的服务端预算为何 ≤ 200

- 事实：pi 的摘要预算推导是 `min(104857, 104800) = 104800`，远大于 200；pi-ai 出站
  （`pi-web/node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js:601-606`）只做
  `options.maxTokens → params.max_tokens / max_completion_tokens`，无窗口钳制；`models.json` 25 个模型
  `maxTokens` 最小 32768；仓库/扩展里都没有 `max_tokens ≤ 200` 的默认值。
- 但代理只能在 ≤200 分支把它判成侧请求（header 分支已排除：`metadata.pluginAgent="pi"`，pi-native 不写该头，
  只有 `dist/agent/opencode.js` 会写 `x-bili-plugin-agent`）。
- 唯一能一锤定音的取证：**开 dump 抓真实 body**——
  ```bash
  # 另起一个 dump 实例（不动正在跑的 :18787）
  ACP_DUMP_BODY=1 ACP_DUMP_DIR=D:/tmp/acp-dumps \
    node "D:/Program Files/Pi Web/data/agent/npm/node_modules/billion-context/dist/index.js" \
    start --host 127.0.0.1 --port 18788
  # 让 pi 走这个代理（BILLION_CONTEXT_PROXY=http://127.0.0.1:18788），触发一次压缩，然后看 dump 里的
  # messages 条数 / tools 是否存在 / max_tokens 实际值
  ```
  局限：想**复现「≤200」**需要 `reserveTokens ≤ 250`（`maxTokens = 0.8 × reserveTokens`），而 pi 的触发线是
  `contextTokens > contextWindow − reserveTokens` ⇒ 需要约 100 万 token 上下文才会压缩，代价不可接受。
  所以 dump 的可行目标只是「看一次正常压缩请求的真实 `max_tokens`」，用于判断矛盾落在 pi 侧还是代理侧。

## 8. 复发时的操作手册（现场 5 分钟）

1. 出现 `side_request_payload_too_large` / `414`-like 大体量报错时，**先别继续在同一会话里压缩**：
   把当前成果落盘（笔记/补丁），然后在新会话里承接（同 workspace 新会话即可）。
2. 想止住空转：`settings.json` 设 `extensionSettings.auto-compact.off = true`（或调大 `cooldownMs`）。
   ⚠ 不要指望调小 `compaction.reserveTokens` 解决——摘要预算与输入体量无关，调小只会让摘要更容易
   命中 token cap（§4 里两条 `generation hit the token cap` 就是那个方向）。
3. 取证顺序：`data/agent/logs/auto-compact.log` → 代理 temp 日志（`bili-proxy-<port>.log`，搜 `side request` /
   `request: 2 msgs` / `[preflight]`）→ 代理会话账本 `…/billion-context/sessions/<proto>/<host>_<hash>.json`。
